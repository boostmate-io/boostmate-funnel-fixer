- Primary Core Offer → Ecosystem row sync runs only via `usePrimaryOfferSync` mounted in BusinessBlueprintModule, writing through `upsertPrimaryOffer` (offerRepository). Why: multiple sync owners caused duplicate writes and dropped edits; DB enforces one primary per blueprint.
- Offer field definitions (labels, value types, enums, controls, tier applicability, AI permissions) live only in `supabase/functions/_shared/blueprintRegistry.ts`; editor-only metadata is additive and must never change Coach prompts (guarded by snapshot + drift tests in `src/lib/registry/`). Why: one source of truth shared by the Blueprint UI, AI Coach and future Offer Editor/Builder.
- Per-tier Offer Editor layouts (tabs, sections, item status, tier wording) live in `OFFER_TIER_LAYOUTS` in the same registry and reference existing definitions by path; Core layout is derived from its sub-blocks. Why: six categories share one editor and one field source without duplicated metadata.
- OfferEditorShell owns presentation and companion dialog interaction only; CoreOfferDialog supplies registry-selected existing tabs and callers supply persistence/flush state. Why: reuse the shell without duplicating fields or save owners.
- Non-Core categories open in `TierOfferDialog`, which renders `OFFER_TIER_LAYOUTS` with existing controls (Stack/Pricing blocks via `only`/`bare`) with the shared offer-scoped Coach; rows without a design are seeded in memory by `designForRow` and only written on edit via `designToRowValues`. Why: one editor and one summary writer per offer, no writes on open.
- CoachPanel portals to document.body; editor-specific companion CSS places it above and alongside the editor, whose Radix modal mode changes only while Coach is open. Why: avoid stacking-context, focus and pointer blocking without weakening unrelated dialogs.
- Primary offer manual saves use useBlueprint's serialized offer queue, and primary Coach writes drain that queue before reading. Why: safe editor closing must reuse the existing persistence owner and retain pending edits.
- Preserve existing Coach transcript/tool/composer primitives for companion-only portal, focus and layering changes; defer AI Elements migration to a separate approved chat redesign. Why: AI Elements' AI SDK message/transport contract is incompatible with the current custom persisted Coach protocol without an unrelated migration.
- Coach offer context is built server-side from `supabase/functions/_shared/offerContext.ts`: the client only claims `activeOffer` (+ draft design); the server re-verifies the offer row by ID and workspace, renders Active Offer / Related Offers / Blueprint as separate layers, and tags persisted turns with an `offer_context` part that the panel checks before applying. Why: suggestions must come from the same offer that scoped write-backs target.
- Offer relationships live only in `public.offer_relationships` (source → target, DB-enforced same workspace); direction labels and per-tier slots live in `OFFER_TIER_RELATIONSHIPS` in the registry, and all reads/writes go through `useOfferRelationships`. Why: one relationship model, independent of offer design autosave.
- Offer relationships are edited only through the shared `OfferRelationshipsSection`, placed via each tier's registry `ecosystem` section (Core: `OFFER_TIER_ECOSYSTEM_TAB`), and saved immediately through `useOfferRelationships`, never via design autosave. Why: one relationship UI for all categories, independent of offer saves.
- Every `useOfferRelationships` instance refetches on the `offer-relationships:changed` window event fired after its own add/remove. Why: editor, cards, Customer Journey and route creation stay in sync without a shared query cache.
- Non-Primary offers use their own Coach conversation (scope `offer`, target_id = offer ID); Primary Core + Blueprint keep the workspace `global` thread, and the server rejects offer threads used for another offer. Why: per-offer history isolation without migrating legacy turns.
- Non-Core Coach writes are validated by `_shared/offerAiPolicy.ts` (`gateOfferCoachWrites` on the server, `applyScopedOfferWrites` with the row's tier on the client), all-or-nothing. Why: one rule set for proposals and applies, keyed to the persisted category.
- Non-Core editors (`TierOfferDialog`) provide the Coach scope (offer ID, real tier, live tab via `getTabId`) only when a save-by-ID `persistWrites` exists; otherwise they render `OfferCoachDisabled`, never the Primary fallback. Why: the Coach must never write to the Blueprint from a non-Core editor.
- Documentation (Academy) lives in `doc_courses`/`doc_lessons`; lesson content is stored as Tiptap JSON and rendered publicly by `DocContentRenderer` (React elements, never HTML), with heading anchors from `extractHeadings` shared by renderer and TOC. Why: safe rendering and one source for anchors; RLS alone gates drafts (admins via `is_app_admin`, public only published lesson in published course).
- Documentation lessons and prompts reuse `DocumentationRichTextEditor` and its shared schema; prompts store Tiptap JSON in `aiPrompt.attrs.promptContent` plus Markdown in `prompt`, loading legacy Markdown on edit and copying safe HTML with Markdown fallback. Why: one WYSIWYG/paste behavior with backwards-compatible storage and clipboard formats.
