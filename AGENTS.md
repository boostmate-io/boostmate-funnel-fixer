- Primary Core Offer → Ecosystem row sync runs only via `usePrimaryOfferSync` mounted in BusinessBlueprintModule, writing through `upsertPrimaryOffer` (offerRepository). Why: multiple sync owners caused duplicate writes and dropped edits; DB enforces one primary per blueprint.
- Offer field definitions (labels, value types, enums, controls, tier applicability, AI permissions) live only in `supabase/functions/_shared/blueprintRegistry.ts`; editor-only metadata is additive and must never change Coach prompts (guarded by snapshot + drift tests in `src/lib/registry/`). Why: one source of truth shared by the Blueprint UI, AI Coach and future Offer Editor/Builder.
- OfferEditorShell owns presentation and companion dialog interaction only; CoreOfferDialog supplies registry-selected existing tabs and callers supply persistence/flush state. Why: reuse the shell without duplicating fields or save owners.
- CoachPanel portals to document.body; editor-specific companion CSS places it above and alongside the editor, whose Radix modal mode changes only while Coach is open. Why: avoid stacking-context, focus and pointer blocking without weakening unrelated dialogs.
- Primary offer manual saves use useBlueprint's serialized offer queue, and primary Coach writes drain that queue before reading. Why: safe editor closing must reuse the existing persistence owner and retain pending edits.
- Preserve existing Coach transcript/tool/composer primitives for companion-only portal, focus and layering changes; defer AI Elements migration to a separate approved chat redesign. Why: AI Elements' AI SDK message/transport contract is incompatible with the current custom persisted Coach protocol without an unrelated migration.
- Coach offer context is built server-side from `supabase/functions/_shared/offerContext.ts`: the client only claims `activeOffer` (+ draft design); the server re-verifies the offer row by ID and workspace, renders Active Offer / Related Offers / Blueprint as separate layers, and tags persisted turns with an `offer_context` part that the panel checks before applying. Why: suggestions must come from the same offer that scoped write-backs target.
